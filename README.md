# hCaptcha 解题框架（hCaptcha Solver Framework）

一个基于 Camoufox + YOLO11x / GroundingDINO 的 hCaptcha 自动化框架。

**请先读「现状」一节再决定要不要用** —— 这个仓库的定位和名字可能给你的预期不一样。

---

## 目标达成状态（先看这一节）

本仓库最初的目标是「自建解题并反复测试直到成功率 ≥95%」。**该目标未达成，实测端到端成功率为 0%。**
这里如实写明状态，避免读者按"能打码"的预期使用。

| 交付项 | 状态 | 证据位置 |
|---|---|---|
| 平台流程骨架（伪装 origin、widget 加载与重试、挑战接入、题面读取、token 提取） | ✅ 实测 10/10 | `tools/eval_harness.py` |
| 点击执行（坐标 → 页面坐标 → 点击 → 像素差分确认） | ✅ live 验证 10/10 | 同上 |
| 拖拽执行（完整指针序列 down→14 段 move→up） | ✅ live 验证（探测命中 62649px，方块随光标移动） | `tools/hunt_drag.py` |
| 可插拔坐标后端 | ✅ 接口与错误路径均已测 | `canvas_backend.py` |
| 整题求解后端（商业服务路线） | ✅ 代码就绪，缺 key 无法实跑 | `token_service.py` |
| **自建坐标生成（pattern 题型）** | ❌ **九项思路/假设全部检验并排除** | 见「最终结论」 |
| **端到端成功率** | ❌ **0%**（三轮 10 次评测、格状子类 0/10 与 0/3） | `research_out/*/summary.txt` |

**要真正达到高成功率，只有两条路**（都需要读者自备，本仓库不代持凭据）：

1. **商业打码服务**（唯一有把握达标）：`export SOLVER_SERVICE_KEY=...` 后跑
   `python tools/eval_service.py 10`。整题求解在服务商侧完成，绕开所有已证伪环节。
2. **自建 + 多模态大模型**：提供 `SOLVER_API_BASE` / `SOLVER_API_KEY` / `SOLVER_MODEL`
   或 GPU，再跑 `python tools/eval_harness.py 10 --attempt-canvas`。
   接线已就绪，但**能否达 95% 取决于模型质量，本仓库不作承诺**。

**怎么核验上面的说法**：否定性结论都可离线复现（`research/` 下的脚本配
`research_out/instances/` 里的实例图，不需要网络）；执行层的 live 验证脚本是
`tools/verify_drag_mechanism.py`（自建 canvas，8 项全绿）与 `tools/hunt_drag.py`。

> 本仓库的价值定位是「**流程框架 + 可行性研究报告**」：把哪些环节已经打通、
> 哪些路走不通、为什么走不通，都留下可复现的证据。它不是一个可用的打码工具。

## 现状：框架可用，但解不了当下的题

这个仓库是一个**流程框架**，不是开箱即用的打码服务。实测结论如下。

### ✅ 已经跑通、可复用的部分

整套平台流程骨架都经过实测验证：

| 环节 | 实现方式 |
|---|---|
| 伪装页面 origin | 用路由拦截在目标 URL 上返回本地 HTML，使 origin/host 与 sitekey 匹配 |
| widget（勾选框）定位 | `iframe[title*='checkbox' i]` → `content_frame()` → `#checkbox` |
| widget 加载重试 | 实测 widget 约 50% 概率不渲染，必须整页重载重试 |
| 挑战 iframe 接入 | `iframe[title='hCaptcha challenge']` → `content_frame()` |
| 题面读取 | `.prompt-text` / `#prompt-question` |
| 令牌提取 | `h-captcha-response`（hCaptcha 同时会写 `g-recaptcha-response`） |
| 交互 | `.button-submit` / `.refresh.button` / `.display-error` |

实测运行：widget 首次加载即就绪 → 点击勾选框成功 → 连续多题均正确读出题面文本。

### ❌ 解不了的部分：hCaptcha 现在不下发照片网格题

用两套 sitekey 跑了 **18 次挑战，0 次**出现经典照片网格
（"Please click each image containing a X"）。实际下发的是：

```
Please click on the TWO icons that break the pattern
Click on the TWO characters that do not follow the pattern
Please drag the screw to the empty joint
Drag the shapes into their outlines
Click the broken spot in the chain
```

DOM 实测：`canvas=1`、`img=0`、`.task=0`。

也就是说，**整道题绘制在一个 `<canvas>` 上**：

- 没有 `.task` 图块元素可以点击
- 没有 `<img>` 子图可以裁剪
- 题型考的是「规律推理」和「拖拽」，不是「逐格目标分类」

这正是 `hcaptcha_solver.py` 里检测管线的核心假设（截图 → 切网格 → 逐格判定 → 点图块），
所以**这条路径对当下的 hCaptcha 无效**。这不是换个更强的检测模型能补的：
需要的不是更准的分类器，而是另一类能力（视觉推理、或在 canvas 上做坐标级拖拽）。

`docs/hcaptcha-canvas-challenge.png` 是其中一道 canvas 题型的截图，可以直观看到长什么样。

### 📋 代码里的分层

| 层 | 状态 |
|---|---|
| 平台流程骨架 | ✅ 实测可用 |
| 照片网格解题路径（`.task` → 截图 → 检测 → 点击 → 提交） | ⚠️ 代码完整，但当下遇不到该题型，**未做端到端验证** |
| canvas 题型 | 🚫 明确判为不支持：打印题面 → 触发 `on_unsupported` 回调 → 刷新重试 → 连续多次后带明确信息退出 |

## canvas 题型结构实测

用 `tools/inspect_challenge.py` 和 `tools/verify_click.py` 探查了两类 canvas 题目，
结论如下（这些是决定后续技术路线的依据）。

### 渲染结构

| 项目 | 实测值 |
|---|---|
| canvas 绘制缓冲 | **1000 x 940** |
| canvas CSS 显示尺寸 | 500 x 470 |
| `devicePixelRatio` | 1 |
| canvas 在 iframe 内的位置 | x=10, y=10 |

注意：缓冲是显示尺寸的 **2 倍**，而且这个 2x **不是** 来自 `devicePixelRatio`（它是 1）
—— hCaptcha 自己按 2x 超采样绘制。

`canvas.toDataURL()` **可用**（未被跨域图片污染），拿到的是 1000x940 的纯净题图：
没有浏览器边框、没有缩放损失、**也没有题面文字**（题面是 DOM 画在 canvas 上方的，
canvas 对应区域是透明的）。这是喂给视觉模型的理想输入。

### 坐标映射

```
canvas 缓冲坐标  ->  除以 2        ->  iframe 内 CSS 坐标
iframe 内 CSS 坐标 + canvas 在 iframe 内的偏移 + iframe 在页面中的偏移  ->  页面绝对坐标
```

实测按这套映射发出的点击，落点与预期完全一致。

### 命中判定：没有 DOM 图块

对 canvas 区域做 10x10 网格采样 `elementsFromPoint`，只出现 4 种元素栈，
且覆盖在 canvas 上方的 6 个元素**全部局限在顶部题面区域**（y=0..110 CSS），
拼图区域上方**没有任何 DOM 元素**。

也就是说：没有 `.task` 之类的图块元素可点，点击必须按坐标发。
点击由 canvas 元素接收，再由 hCaptcha 自己的 JS 做命中判定。

### 选中状态：DOM 里看不到

点选前后扫描 `[aria-checked]`、`[aria-pressed]`、`[data-selected]` 以及类名含
select/mark/active/check 的元素：**全部为 0 个**。选中状态完全保存在 JS 内部，
只体现在 canvas 重绘上。挑战 iframe 的 `window` 上也没有暴露可用的状态对象。

**所以判断「点中了没有」的唯一途径是重新抓 canvas 做像素比对。**

### 坐标点击有效（已验证）

`docs/canvas-click-challenge.png` 是一道 "Please click on the TWO icons that break the pattern"：
一堆不同旋转角度的火箭图标。"TWO" 只是个提示，实际选中上限更高。

在拼图区域按 3x3 网格依次点击，每次点击后重新抓 canvas 与基线做差分：

```
第 1 点 (0.20,0.35)  变化 2712px   ✅ 出现选中标记
第 2 点 (0.50,0.35)  变化 5418px   ✅ 又加一个（增量 ~2710px）
第 3 点 (0.80,0.35)  变化 8146px   ✅ 又加一个
第 4 点 (0.20,0.55)  变化 10864px  ✅ 又加一个
第 5~9 点            变化 10882px  ❌ 不再变化（选中已达上限）
```

`docs/canvas-click-selected.png` 是点完之后的画面：**4 个圆形叉号标记，
位置与 4 次点击的坐标逐一对应**。这证明：

1. 坐标点击被正常接收，落点精确；
2. 每次选中在 canvas 上留下约 2710 像素的固定大小标记；
3. 选中数量存在上限，达到后被静默忽略（后续点击不报错也不生效）。

### 结论：可以走坐标级操作，难点在「点哪里」

点击通道和反馈通道都打通了：按坐标点击有效，且能用「重新抓图 + 差分」确认选中。
真正剩下的是视觉推理本身——以那道火箭题为例，需要判断「哪两个图标的旋转角度
不符合整体规律」。

一个值得先试的方向：这类图标题的图标是**高对比度白色轮廓、形状相同、只有旋转不同**，
所以可以用传统 CV 而不是大模型来解——分割出每个图标 → 估计各自旋转角 →
找出偏离规律的那几个。这比接一个通用 VLM 便宜得多，也更可控。
但这个假设还没验证（规律到底是旋转序列、位置排列还是别的，需要再抓几道题确认）。

## 为什么 95% 这个目标达不到

必须说清楚：**在当前条件下，95% 成功率不是一个可达目标。**
这不是"再调几轮"的问题，下面是具体依据。

### 1. 旋转估计路线已被实测证伪

pattern 题型要先量出每个图标的旋转角。实测结果：

| 检查项 | 结果 |
|---|---|
| 图标分割 | ✅ 20/20 全中，无误检（见 `docs/` 标注思路） |
| 估计器在**合成**旋转上 | ✅ 误差 0°，相似度 0.999 |
| 估计器在**真实**图标上 | ❌ 判别余量 **0.0002**（需要 > 0.05） |

尝试过三种配置，判别余量始终在 0.0005~0.0016：

```
fill=False blur=0.8 area=2000 : 中位 0.0005
fill=True  blur=0.8 area=2000 : 中位 0.0016
fill=True  blur=1.5 area=3000 : 中位 0.0011
```

**根因不是分割或模糊**：火箭这类图标本身是「矮胖 + 近似镜像对称」的，
旋转一个小角度后与自身的重叠度几乎不变，所以旋转角度在像素上就是个弱信号。
换更好的匹配器也补不上——信息本身不在那里。

（之前我一度以为"角度看起来像平滑场"，那是把噪声当信号读了。
单元测试才暴露出真实判别余量。）

### 2. 即使量准了角度，规律仍然未知

"哪两个破坏规律"取决于规律本身。10 次里出现了 4 种不同题面，
规律可能是旋转序列、局部平滑场、位置排列……每种都要单独逆推，
而且**没有本地真值**——唯一的裁判是 hCaptcha 服务端的通过/不通过。

### 3. drag 题型完全没动

10 次里 4 次是拖拽题（"drag the screw to the empty joint"），
需要识别源物体和目标位置、再合成 pointer down/move/up。
这是另一套能力，目前一行代码都没有。

### 4. 能力上限受环境影响

- 本机 **CPU-only** torch，连 GroundingDINO-tiny 推理都明显慢；
  能胜任这类视觉推理的模型（大 VLM）体积是 GB 级，CPU 上跑不动。
- 本机 **HuggingFace 直连被墙**（只有 `hf-mirror.com` 可用）、
  GitHub 直连被墙 —— 想引入一个专门训练的模型，先得过网络这一关。
- 商业打码服务能做这些题型，靠的是**专门训练的大模型 + 人工兜底**，
  不是通用检测器加几轮调参。

### 5. 市面方案调研：结论是「必须用托管的大模型」

对最有代表性的开源项目 hcaptcha-challenger（QIN2DIM，一直在维护到 2026-08）
做了调研：

- 它的挑战类型分类是：`image_label_binary`（ResNet ONNX）、
  `image_label_area_select`（YOLOv8 ONNX 检测/分割）、
  `image_label_multiple_choice`（ViT ONNX 零样本）、`image_drag_drop`。
- 但**最近的提交已经把默认模型换成 Gemini 3.7 Flash**
  （"feat(models): update default models to Gemini 3.7 Flash"），
  另外还有 "Gemini 3"、"dynamic thinking budget"、"retry logic for spatial challenges"。
- 它自带的 ONNX 模型是 2 月的产物，针对的是旧版挑战分类。

也就是说：**这个领域里最专注、维护最久的项目，最后也把难题交给托管的大型
多模态 LLM 去解**。这和我本地三轮实验的结论一致。

### 6. 本地小模型（Moondream2）实测：已排除

第一次测出的是乱码，但那是我这边的环境问题，不能当作能力结论。这轮把它修好并
测出了真实数字。

**先修环境（记录以备复现）：**

| 问题 | 原因 | 处理 |
|---|---|---|
| 输出退化成复读（`1KeKeKeKe...`） | 模型 config 声明 `transformers_version: 4.52.4`，而主环境是 5.17.0 | 建隔离环境 `.venv-vlm` 装 transformers 4.52.4（不动主环境，避免影响 GroundingDINO） |
| `FileNotFoundError: transformers_modules/moondream2/layers.py` | 动态模块缓存只拷进去 9/17 个 .py 文件 | 把本地模型目录的 `*.py` 同步进 `~/.cache/huggingface/modules/transformers_modules/moondream2/` |

**修好之后的真实能力与耗时**（图缩到 448x313，CPU）：

| 查询 | 回复 | 耗时 |
|---|---|---|
| How many rocket icons are in this image? | "There are fifteen rocket icons in the image." | 106.1s |
| Which rocket icon is different from the others? | "Top center" | 115.5s |
| `point("rocket that does not follow the pattern")` | **返回 15 个点**（前3: 0.42/0.82, 0.50/0.71, 0.59/0.82） | 185.4s |

模型是**真的能看懂图**——能正确数出数量（15 个），说明之前那次乱码确实只是版本问题。

但两点让它无法用于本题：

1. **接口语义不对**。`point()` 是「实例定位」原语：给它一个名词，它返回该物体的
   **全部**实例——所以问「不符合规律的那个」它返回了全部 15 个点。
   它没有「推理出异常项」这个能力。真正的推理走 `query()`，而 `query()` 给出的是
   "Top center" 这种**模糊散文**，不是可点击的两组坐标。
2. **耗时不可接受**。448px 的小图单次 106~185s（CPU）。要组成「先定位 15 个图标、
   再两两比较」的策略，需要约 190 次查询 —— 完全不现实；即便单次查询，
   也可能撞上验证码的超时。

**一个有意思的交叉验证**：模型对「哪个不一样」答 "Top center"，
而我之前的像素分析里，偏离最大的也正是顶部中央那枚（bbox 139px vs 其余约 80px，
相似度中位 0.420）。两个完全不同的方法指向同一个图标，说明它确实视觉上显著。
但那只说明「它看起来不一样」，不等于「它就是题目要的那两个」——
而后者需要真值，本机没有。

（顺带记两个环境坑：`huggingface_hub` 的 `snapshot_download` 下 3.6GB 大文件会
卡死，改用 `curl -C -` 续传能跑到 45MB/s；`models/` 与 `.venv-vlm/` 都已加入
`.gitignore`。）

本次会话我**三次把结论说得比数据支持的更强**，且三次都是自查才发现：

| 把 n=5 的列均值梯度说成"系统性位置偏差" | 小样本当规律 |

## 最终结论

**在「本机、CPU、无外网 API」的条件下，95% 成功率无法达成。** 依据是上面九项
彼此独立的证据，而不是单点失败：

| 尝试 | 结果 |
|---|---|
| 1. 掩膜重叠 + 旋转扫描 | ❌ 判别余量 0.0005 |
| 2. 转角函数（曲率互相关） | ❌ 判别余量 0.0082（阈值需 >0.05） |
| 3. 两两相似度矩阵聚合 | ❌ 找到的是分割噪声（参考图标 bbox 139px vs 其他 80px、星云区污染），不是题目异常 |
| 4. 尺寸/形状异常假设 | ❌ 已测并排除（见下） |
| 5. 原始像素匹配滤波（绕开分割） | ❌ 无任何图标达离群阈值（见下，这是最干净的一次否定） |
| 6. drag 题型 | ✅ 动作已实现并 live 验证（探测命中 62649px，方块随光标移动）；缺的同样只是坐标 |
| 7. 市面方案 | ❌ 最专注的开源项目已改用托管 LLM（Gemini 3.7 Flash） |
| 8. 本地小 VLM | ❌ 接口语义不匹配 + 106~185s/次，速度上不可行 |
| 9. 格状「字符」子类（3 个假设：多数表决 / 方向自洽判据 / 格框对齐） | ❌ live 0/10 与 0/3；格框假设离线 n=5 净负面。立得住的失败原因：**候选分几乎并列**（live top 分相邻仅差 0.001~0.027），取最低两个接近随机 |

关于第 5 项（**最干净的一次否定**）：前四种思路都建立在**分割掩膜**之上，
而我已经量化证明瓶颈就在分割（星云区图标描边被抗锯齿混色，颜色法失效）。
于是改用**匹配滤波**——完全不做分割，直接在原始像素上做旋转模板匹配
（`cv2.matchTemplate` + `TM_CCOEFF_NORMED`，对亮度/对比度不变，因此不怕
星云与深空背景不同；取多模板多角度的最高响应作每个图标的得分）：

```
响应得分 中位 0.682  区间 [0.351, 1.000]  离散度 0.322
稳健 z < -3.5 的图标数: 0   （题目要找 2 个）
最低的几个 z 仅 -0.96 / -0.89 / -0.70
```

**零个图标达到离群阈值** —— 分布是连续渐变，没有干净的异常项。
这排除了"之前的信号是被分割噪声掩盖了"这一可能：即便绕开分割，
信号也不在「字形与其他明显不同」这个维度上。

（顺带修正：脚本原先的"断层"启发式在这种连续分布上会误报"候选较明确"，
与 z 统计矛盾。已改为以稳健 z 为准、断层仅作参考。这类启发式在没有
分布先验时不能单独用作判据。）


关于第 4 项（方法学盲点，值得单独记）：我前面的相似度匹配按 `sqrt(面积)` 归一化，
**这一步会把尺寸差异主动抹掉**。如果题目考的是某个图标尺寸不一样，正好被我消掉了。
线索也支持这个方向（顶部中央那枚 bbox 宽 139px vs 其余约 80px；Moondream2 被问
"哪个不一样"时独立答 "Top center"）。

于是用 **bbox 对角线 `sqrt(w²+h²)`** 做探针 —— 对刚体形状它与旋转无关，
是干净的尺寸度量。实测（`research/size_outliers.py`）：

- 对角线稳健 z 最大仅约 ±2.9，**没有任何图标超过 3.5**
- 两个最大的正是已知的分割污染成分（139x72 那个宽扁块）
- 18% 的对角线离散度与分割噪声一致，不是干净的「2 个离群」

=> 尺寸/形状差异假设排除。这一维度测过了，不是答案。


### 一个新发现的题型：格状「字符」型（有潜力，但尚未解出）

做推广性检验时（用 8 道题替代原来的单实例）发现：同一句题面
`Click on the TWO characters that do not follow the pattern` 对应**两种不同布局**：

| 布局 | 样子 | 可用信号 | 状态 |
|---|---|---|---|
| 散点型 | 一堆同字形图标以不同旋转角散布在场景里 | 旋转 —— 太弱 | ❌ 五种思路全部失败 |
| **格状型** | **4x4 白色方块格，每格一个完全不同的卡通角色** | **颜色+外形 —— 很强** | ⚠️ 见下 |

格状型在结构上**明显更适合算法求解**：

1. 格子由白色方块分隔，边界清晰，不必在复杂背景上分割
2. 角色之间色彩与轮廓差异巨大，而"是否同一角色"是个强信号
   —— 与散点型"只差一个旋转角"的弱信号不是同一量级
3. 规律很可能是「每列/行重复同一角色」，异常即偏离本列多数的那两格 ——
   按位置分组做多数表决即可，不需要理解"规律"本身

**但我用多数表决做了一次，没有成功**，如实记录首次尝试：

```
按列表决：相似度区间 0.788 ~ 0.915   —— 挤在窄带里，无清晰离群
按行表决：相似度区间 0.741 ~ 0.772   —— 更窄
两方向候选只有 (3,3) 重合，判定为不一致
```

而且格提取本身有问题：**检测到 30 个角色块却只填满 16 格**，说明角色被
过度分割（一个角色被拆成多个连通域），取到的块可能只是角色的一部分。

### 定位到 0% 的机制：判据只拿到「部分正确」，而题目要求两个都对

这一步查的是链条里一处**从没验证过的环节**：我验证过"点击能被 canvas 接收"
（像素发生变化），但**从没验证过点击是否落在我想点的那一格上**。
若格心坐标与格子实际位置有系统性偏移，即使判据选对格子也会点到隔壁 —— 直接解释 0/3。

用 `research/verify_pick_coords.py` 把 16 个格框与候选格心画到图上核对：

```
pat_01 候选=[[0,2],[1,3]]  格心落在格内=[True, True]
pat_02 候选=[[2,3],[1,2]]  格心落在格内=[True, True]
pat_04 候选=[[2,3],[1,3]]  格心落在格内=[True, True]
pat_06 候选=[[2,1],[3,2]]  格心落在格内=[True, True]
pat_08 候选=[[3,1],[2,2]]  格心落在格内=[True, True]
=> 5/5 全部落在预期格内，「点到隔壁」这个假设被排除。
```

再逐题肉眼核对"选中的是否真是异常项"（`research_out/verify_picks/*.png`）：

| 实例 | 判据选的 | 肉眼看应为 | 命中 |
|---|---|---|---|
| pat_01 | (0,2)、(1,3) | (0,2)、(1,3) | **2/2** |
| pat_04 | (1,3)、(2,3) | (1,3)、(2,2) | **1/2** |

pat_04 的读法：第 1 行是 青/青/青/**蓝机器人**，异常是那个蓝的（判据选对）；
第 2 行是 兔/兔/**青怪**/兔，异常应是 (2,2) 那个青怪，而判据选的是 (2,3) 的兔子。

**两个可肉眼核对的实例合计 3/4 个单点命中。** 而 hCaptcha 要求**两个都点对才通过**，
所以配对成功率约等于单点正确率 p 的平方。

### ⚠️ 更重要的更正：上面这张"真值表"本身靠不住

上表那两行"肉眼应为"是我按"每行重复同一角色"**推断**出来的，不是 hCaptcha 给的答案。
我原本以为它足够可靠，但做了两次**控制变量实验**后发现该假设站不住：

**实验一：只换特征，不换算法。** 把手写的"颜色直方图 + 灰度相关"换成
**CLIP 视觉嵌入**（大规模图文对训练出的语义特征，512 维，理论上远强于手写特征）：

```
特征=hand  选点=top2  -> 命中 3/4   (pat_01:2/2  pat_04:1/2)
特征=clip  选点=top2  -> 命中 3/4   (pat_01:2/2  pat_04:1/2)   <- 完全没变
```

**实验二：只换选点方式，不换特征。** 怀疑"同行内细微渲染差异产生的伪偏离"
与真异常混在一起，于是把"取 top-2"改成"按偏离值排序后取最大断层之上的项"：

```
特征=hand  选点=gap   -> 命中 2/4   (pat_01:1/2  pat_04:1/2)   <- 更差
特征=clip  选点=gap   -> 命中 3/4   (pat_01:2/2  pat_04:1/2)   <- 无改善
```

（预登记判据是"两例都 2/2 才算改进"，即 4/4。四组**没有一组达到**。）

**关键推论**：hand 与 clip 是两套**完全不同的特征空间**，却一致地在 pat_04 上选出
`(3,2)` 而漏掉我推断的 `(2,2)`。两套独立表示指向同一格，更像是**那一格确实视觉上不同**
—— 也就是说，**错的是我的"真值推断"，不是判据**。

所以正确的说法是：**我根本没有真值**。hCaptcha 服务端的通过/不通过是唯一真源，
而我从没提交对过任何一次，所以无从校准。上面那张表、以及它所支撑的
"3/4 命中率"与"配对成功率约 p²"的整段推论，**全部建立在未经验证的推断之上，应当作废**。

（工具：`research/clip_cells.py`、`research/select_by_gap.py`，均可离线复现。）


⚠️ **但要注意：3/4 这个离线估计太乐观，解释不了 live 的 0/13。** 用二项分布核对：

```
单点 p=0.75 -> 配对≈0.562 -> P(13 次全败) ≈ 0.0000   <- 几乎不可能
单点 p=0.60 -> 配对≈0.360 -> P(13 次全败) ≈ 0.0030
单点 p=0.50 -> 配对≈0.250 -> P(13 次全败) ≈ 0.0238
单点 p=0.40 -> 配对≈0.160 -> P(13 次全败) ≈ 0.104    <- 与 0/13 相容
单点 p=0.30 -> 配对≈0.090 -> P(13 次全败) ≈ 0.294    <- 与 0/13 相容
```

也就是说：**只有当单点命中率低到 0.4 以下时，0/13 才是正常的**；
而我肉眼估的 3/4（n=2）明显偏高。两种可能：(a) 真实 p 比我估的低得多
（n=2 的估计本就不可靠），(b) live 路径里还有一处我没发现的失败。
**这两种我现在都无法区分** —— 因为 `eval_grid.py` 当时没保存挑战图，
失败案例没法事后分析（这正是下一段要补的仪器缺口）。

**所以「0% 的机制」只能说到这一步**：判据确实只拿到部分正确，
但**"部分正确"具体到什么程度、以及 live 是否还叠加了别的失败，尚未确定**。

**一个仪器缺口（已修）**：`eval_grid.py` 原先不保存挑战图，
导致 live 失败无法事后分析 —— 这也正是上面 (a)/(b) 无法区分的原因。
现已让它在每次尝试时把 canvas 存到 `research_out/eval_grid/trial_*/`，
下次跑 live（无论谁跑）失败案例都能离线复查。

（caveat：上表"肉眼看应为"是我按"每行重复同一角色"这一读法推断的，并非 hCaptcha
给出的真值 —— 我没有真值，只能这样估。pat_04 的第 0/3 列各行角色全不相同，
所以行方向是唯一可行读法，据此推断相对可靠。）

### 失败原因追查（含一次我自己的过度推断，已在下一节更正）

上面那个"候选取集中在第 1~2 列"的反常，我没有停在猜测，而是做了可离线检验的对照
（`research/diagnose_bias.py`，用 8 道已存实例中能提出 16 格的 5 道）：

```
各列平均偏离: 0.0988 / 0.1015 / 0.1521 / 0.1653   极差 0.0665
各行平均偏离: 0.1161 / 0.1162 / 0.1351 / 0.1504   极差 0.0343
top4 候选列分布 [3,5,5,7]（随机期望每列 5）
```

列 2~3 的偏离度比列 0~1 **高约 65%**，且 top 候选偏向后段列。
也就是说：**偏离度这个度量里混进了与内容无关的位置成分** ——
它排序的不完全是"哪个角色不合群"，还掺了"在哪一列"。

这比"判据不够聪明"具体得多，也直接解释了 live 的 0/3。

**机制验证与部分修复**（`research/diagnose_bias2.py`）：推测是页面背景的颜色渐变
被一起算进了格块。于是裁块后先抠掉背景（只留强饱和/偏暗的角色前景）再比：

```
原始（含背景）     各列极差 0.0665   各行极差 0.0343
抠掉背景（只留角色） 各列极差 0.0588   各行极差 0.0298   （仅降约 12%）
```

**偏差只减弱、没有消除**：列 2~3 仍显著偏高（0.116/0.134 对 0.088/0.075）。
所以背景色调是**一个**成因，但不是主因；残余的位置依赖还在。
最可能是格框本身有列相关的偏移（k-means 由块质心定格，外列裁切与内列不一致），
导致不同列的裁块对齐程度不同 —— 这会直接压低某些列的相似度。

**结论**：格状子类失败的机制已定位到"度量含位置成分 + 残余来源待查"，
但**修好它还需要一轮针对格框对齐的排查**。我不把这轮算作成功率上的进展。

### ⚠️ 更正：我先前声称的「位置偏差」不成立

我在上一节写过"列 2~3 的偏离度比列 0~1 高约 65%，存在系统性位置成分"，
并据此做了两轮追查（背景抠除、边框吸附）。**这个前提本身是被我高估的，现予更正。**

把每个实例单独看，峰值列并不一致：

```
pat_01 列均值 [0.086, 0.106, 0.140, 0.124]  峰值列=2  最低列=0
pat_02 列均值 [0.103, 0.017, 0.098, 0.136]  峰值列=3  最低列=1
pat_04 列均值 [0.074, 0.000, 0.164, 0.284]  峰值列=3  最低列=1
pat_06 列均值 [0.152, 0.198, 0.227, 0.220]  峰值列=2  最低列=0
pat_08 列均值 [0.079, 0.187, 0.133, 0.062]  峰值列=1  最低列=3   <- 峰值不在后两列
```

峰值列 = [2, 3, 3, 2, 1]，最低列 = [0, 1, 1, 0, 3] —— **没有一致的偏好列**。
若真是固定的位置性伪影，所有实例都该偏向同一列，事实并非如此。

只有 4/5 的峰值落在后两列，均匀假设下该结果的概率 **p = 0.188（不显著）**。
也就是说：我从"5 个实例求平均"里看到的那个梯度，**很可能只是小样本平均的产物**，
不是被证实的位置偏差。

**因此**：上一节那两轮追查（背景色调、格框对齐）是建立在未证实的前提上的；
边框吸附得到"净负面"这个结论本身仍然有效（它确实更差），
但"为了消除位置偏差"这个动机不成立。这段推理链我保留在文档里作为记录，
不当作结论。

**真正立得住的失败原因**只有一条，而且它有 live 直接证据 ——
**候选分几乎并列，所以"取最低两个"接近随机取**：

```
live 三次的 top 分: [0.3277, 0.3009, 0.1776, 0.1769]
                    [0.34,   0.2853, 0.229,  0.1297]
                    [0.1584, 0.146,  0.1385, 0.1153]
```

第一题第1与第2只差 0.027，第三题前四名挤在 0.158~0.115 之间。



### 第三个假设（格框对齐）：结论仍有效，但动机已作废

顺着上面那条"残余最可能来自格框对齐"的线索做了一轮（`research/diagnose_bias3.py`）：
方块底之间的**灰色细边框**是与内容无关的几何锚点，于是由质心格阵估出格距后，
沿列/行投影暗度、把边界吸附到最暗处，用它替代"质心定格"。

结果**净负面**，假设不成立：

```
质心定格（原实现）  各列极差 0.0665   各行极差 0.0343   （偏离均值 0.099~0.165）
边框吸附（本轮）    各列极差 0.0491   各行极差 0.0884   （偏离均值 0.124~0.173）
```

列极差虽降 26%，但**行极差恶化到 2.6 倍**，且整体偏离值普遍升高
（列0 由 0.0988 升到 0.1698）—— 说明吸附后的格子**对齐更差**了，
行方向的边界被吸到了错误位置。所以：格框对齐这个成因**未获证实**，
且按此实现的边框吸附是个更差的方案，不应采用。

**至此格状子类的三个假设都已检验并排除**：

| 假设 | 检验 | 结果 |
|---|---|---|
| 列/行多数表决 | live n=10 | ❌ 0/10 |
| 先判方向自洽再找偏离 | 离线 n=1 通过 / live n=3 | ❌ 3 次全错 |
| 格框对齐（边框吸附） | 离线 n=5，指标对比 | ❌ 净负面（行极差 2.6 倍） |

立得住的失败原因只有一条，且有 live 直接证据：**候选分几乎并列**
（live 三次的 top 分相邻仅差 0.001~0.027，见上一节），"取最低两个"接近随机取。
至于"偏离度是否含位置成分"——**已撤回**，p=0.188 不显著，那只是小样本平均的产物。



上一轮把瓶颈定位到「判据」——候选分几乎并列（0.693/0.700/0.715/0.727），
"取最低两个"等于随机取。回看唯一能肉眼核验的那道题（`pat_01`）发现症结：
**我把列与行两个方向平均了，而其中一个方向本来就不自洽**，信号被稀释。

改成先判方向、再在该方向找偏离（`rule=axis`）：

1. 建 16x16 两两相似度矩阵
2. 对「列」和「行」分别算自洽度：每条线取与其他格平均相似度最高的那个作"主流角色"，
   该线的自洽度 = 主流角色与线内其它的平均相似度
3. 选自洽度更高的那个方向，异常 = 与线上主流角色最不像的格子

**离线自检（在 pat_01 上）是成功的**：

```
picks = [[0,2], [1,3]]          <- 与我肉眼判定的真异常完全一致
列自洽 0.848 > 行自洽 0.712      -> 正确选了列方向
top 分 [0.3871, 0.2879, ...]    <- 第1与第2差 0.10，不再是 0.001 级并列
```

**但 live 没有验证成功**，如实记录（完整跑完，非中途停止）：

```
轮数 100（pattern 97 / other 3）-> 只遇到 3 道格状题（该次会话约 3%，注意此比例跨会话波动极大，见下）
3 次尝试，3 次都回 'Please try again.'   0/3
  picks=[[1,2],[0,2]]   top=[0.3277, 0.3009, ...]
  picks=[[2,2],[1,2]]   top=[0.34,   0.2853, ...]
  picks=[[1,2],[1,1]]   top=[0.1584, 0.146,  ...]
```

**一个值得记下的反常**：3 道题的候选取全都落在**第 1~2 列**，从没碰过第 0 或第 3 列。
如果异常位置在题间是随机的，不该出现这种聚集。这提示"偏离度"排序可能**系统性偏向某个区域**
（比如画面渐变、光照或格框裁切的固定偏移），而不是真的在看内容。
第三次的 top4 又挤在一起（0.1584/0.146/0.1385/0.1153），仍是接近并列。

另外格状题的占比**在不同会话之间差异极大**，任何单次会话的数字都不能当作普遍比例。
把三次实际统计合起来看（`_grid_eval*.log`、`_instances.log`）：

| 批次 | 提出 16 格（格状型） | 格提取失败（散点型） | 格状占比 |
|---|---|---|---|
| 第一批 | 5（由 8 张实例图事后判定） | 3 | ~63% |
| 第二批 | 10 | 19 | ~34% |
| 第三批 | 3 | 94 | ~3% |

**63% / 34% / 3% —— 相差近 20 倍。** 合并约 18/134 ≈ 13%，
但更重要的是这个比例显然由会话级因素决定（IP/会话信誉或服务端的题型调度），
**不是稳定常数**。我先前写的"只占约 3%"是拿单次会话的数字当普遍比例，这里更正。

对结论的影响：凑 100 道格状样本按合并比例约需 700~800 轮挑战，
按 3% 则需 3000+ 轮 —— 无论取哪个都说明**不靠凭据、单靠刷题凑统计样本不现实**。

**结论：判据的改进在离线自检上成立（n=1），但 live 明确不支持（n=3 全错），
且出现了疑似系统性位置偏差。我不把它算作进展。**



**格提取修好了**（第三版 `research/grid_cells3.py`）。关键是**放弃亮度阈值**——
方块底与页面背景的亮度本来就重叠，量也量不准。改用几何思路：

1. 只认**强饱和**像素（角色都是鲜艳配色；背景纹理与灰阶线条都不满足）
2. 把所有角色块的质心 x 聚成 4 簇、y 聚成 4 簇 → 4 条列线 + 4 条行线
3. 列线 x 行线（笛卡尔积）= 16 个格心，格边长取 `0.9 * min(列距, 行距)`

这一步成功的判据是**几何自洽**：实测列线 265/423/581/738（列距 157）、
行线 114/272/428/584（行距 156）—— 间距几乎相等，正是正确格阵该有的样子；
角色块也正好 16 个。并已用 `research_out/grid3/cells.png` **逐格肉眼核验**：
16 格各含一个完整角色，无空白、无残缺。(前两版分别失败于背景漏入和阈值过严。)

用块的位置定格、而不是块的归属，还顺带免疫了第一版"一个角色被拆成多块
导致某格被覆盖"的问题：碎片的位置仍在所属行列附近，只轻微扰动簇心。

**首次实现闭环**：`tools/eval_grid.py` 提取格子 → 按规则选 2 格 → 按坐标点击 →
提交 → 读 hCaptcha 回执。这是整次会话里第一次能对 pattern 子类真正提交并拿到真值。

**但结果是 0/10**，如实记录，两种规则各 5 次全错：

```
规则 col   （与本列其它格最不像的 2 格）: 0/5
规则 global（与全场所有格最不像的 2 格）: 0/5
回执全部为 'Please try again.'
```

**失败原因已定位**：候选分几乎并列。例如某题 top 分为
`0.693 / 0.700 / 0.715 / 0.727`，另一题为 `0.571 / 0.574 / 0.579 / 0.590`
—— 相邻候选只差 0.001~0.01，**"取最低的两个"等于随机取**。
也就是说：瓶颈已经从"格提取"转移到了"**判据**"。
即便格框完美，两两相似度排序也不能指出真正异常的那两格。

可能的解释：规律是**位置性的**（比如沿对角线递变），必须对"排布"建模，
而不是比较两格像不像；也可能我的相似度（颜色直方图 + 灰度相关）对
"形状不同但配色相近"的角色分辨不足。要往下走得换判据，
而不是再修提取——这一点已经明确。



第二轮专门修格子提取（`research/grid_cells.py`，思路改为"先找白方块底，
而不是先找角色"），但三次都没成功：

| 尝试 | 方法 | 失败原因 |
|---|---|---|
| 1 | 先检角色块，再往 4x4 里塞 | 过度分割：30 块 -> 16 格，取到的块可能只是一条胳膊 |
| 2 | `V>205 & S<60` 找白方块 | **背景漏进来了**：包围盒变成整幅图 1000x700，切分边界全错 |
| 3 | `V>235 & S<40`（据实测取样定的阈值） | **过严**：包围盒只剩 134x124，其实是某个角色的一小块 |

第 3 次的"实测取样"本身是错的：我取样时凭肉眼猜了"方块底"的区域，
结果取到了角色像素（其中一块样本的 S 中位数是 115，明显是彩色角色），
于是量出来的阈值并不代表方块底。**量了，但量错了地方**——
这和前面"看断层就当有离群"是同一类错误。

验证方式是把 16 个格子拼成一张图直接看（`research_out/grid2/cells.png`）：
结果是 16 张空白/残缺的粉色碎片，即**整块其实只是某一个角色的局部**，
所以那一轮算出来的相似度（0.529~0.806）**全部作废，不能当作发现**。

**结论：格状题型仍未解出，且格提取这个前置步骤本身还没做对。**
下一步不该再调亮度阈值，而应该换更稳的几何线索：
用灰边做边缘/梯度检测直接找格线，或先用角色块质心估计格距再反推格框。

工具：`research/grid_characters.py`（第一版）、`research/grid_cells.py`（第二版）。
实例图：`research_out/instances/pat_0[1-8].png`。

有两条，第二条把握大得多。

**路线 A：自建求解（接多模态大模型）** —— 需自行解决坐标生成

1. 一个多模态 LLM 的 **API key**（会产生费用）；
2. 或一块 **GPU** + 足够大的本地 VLM（7B 以上，且需解决 transformers 兼容问题）。

接线已备好：`canvas_backend.py` 的接口就是「给一张 canvas 图，返回要点的坐标」，
换成云端模型只需替换坐标生成部分；点击、拖拽、像素差分验证、评测 harness
都已实测可用。但**能否达到 95% 取决于模型质量，无法事先承诺** ——
pattern 题要求「哪两个图标破坏规律」近乎全对，而这正是五种 CV 思路都失败的地方。

**路线 B：直接调用商业打码服务** —— 唯一有把握达到高成功率的路线

已实现**两套协议**，并把厂商相关的字段名全部做成可配置（`token_service.py`）：

| 协议 | 端点 | 说明 |
|---|---|---|
| v2 任务式（默认首选） | `POST https://api.2captcha.com/createTask` + `getTaskResult` | 2captcha 现在主推；鉴权 `clientKey`，sitekey/url 放在 `task` 对象里（`websiteURL`/`websiteKey`） |
| 老式 | `in.php` + `res.php` | 鉴权 `key`；`method` 与 sitekey 参数名可配 |

默认 `auto`：先试 v2，失败自动回退老式 —— 两套协议接口主机与字段都不同，互为兜底。

> ⚠️ **一个我无法核实的地方，请留意**：查公开文档时，2captcha 的 hCaptcha 专页返回 404，

> 因此所有相关名字都可覆盖，且 token 提取是递归找"像 token 的字段"，
> 不写死字段名：

```bash
export SOLVER_SERVICE_API=auto|v2|legacy        # 协议选择
export SOLVER_SERVICE_TASK=HCaptchaTaskProxyless # v2 的 task.type
```

## 使用

```python
from hcaptcha_solver import solve_hcaptcha

def on_unsupported(prompt: str):
    # 遇到 canvas 题型时会被调用，可以在这里接你自己的求解器
    print("拿到题面了:", prompt)

token = solve_hcaptcha(
    sitekey="a5f74b19-9e45-40e0-b45d-47ff91b7a6c2",   # hCaptcha 官方演示页
    url="https://accounts.hcaptcha.com/demo",
    headless=True,
    on_unsupported=on_unsupported,
)
print(token)
```

或直接跑内置的演示用例：

```bash
python hcaptcha_solver.py
```

### 路径替换成自己的求解器

遇到不支持的 canvas 题型时，`on_unsupported` 会收到题面文本。

再把结论回写到挑战框（canvas 题型需要坐标级点击，而不是点图块元素）。

## 已知限制

1. **「点哪里 / 从哪拖到哪」未解决**（主要限制）—— 点击与拖拽的**执行**都已验证
   可用，缺的是决定坐标的后端。pattern 题型的传统 CV 路线已量化证伪；
   本地小模型已实测排除；drag 题型的动作已实现并做了机制级验证。
2. **drag 题型的 live 验证 ✅ 已完成** —— 动作已实测被 hCaptcha 的 canvas 接收。
   过程曲折，记录如下（含两次错误结论的更正）：

   - **拖拽题很稀有**：跨 4 组配置 + 两轮长扫描，共 61 题只有 1 道拖拽
     （58 pattern / 2 other / 1 drag），约 1.6%。所以复现一次需要跑上百轮刷新。
   - **踩过的坑一：起手点落在空白处**。第一次拿到拖拽题时从画面正中起手，
     得到 0 像素变化，我判断为"手势未被接收"——**这个结论是错的**。
     看 before.png 才发现那类题的布局是「左侧面板放方块 + 右侧面板虚线轮廓」，
     画面正中是右侧面板空白，根本没抓住东西。
   - **踩过的坑二：按颜色找方块不可靠**。改成检测米黄色方块后，遇到另一种布局
     （全幅场景、木条堆在中间、右缘圆形 Move 手柄），检测器把暖色**背景**当成了
     方块；后来又遇到方块是**浅蓝色**的版本。颜色/位置都不能写死。
   - **最终解法：与布局无关的抓取探测**。不猜方块在哪，而是对若干候选起手点
     逐个「按住 → 小幅移动 → 按住不放时抓帧比对」。只要任意一个候选让画面变化，
     就证明手势被接收。实测结果：

     ```
     探测 [中心]               起手(500,517) 按住中变化=0      松手后=0      —
     探测 [中部偏右下(木条堆)]  起手(600,583) 按住中变化=0      松手后=0      —
     探测 [变体A 上块]         起手(135,376) 按住中变化=62649  松手后=59081  ✅
     ```

     命中在轮次 61、题面 "Drag the shapes into their outlines"。变化区域
     x[46..333] y[253..525]，正好是方块原位加移动轨迹。对照图
     `research_out/drag_hunt/compare_round61.png` 可直观看到方块跟着光标移动、
     Move 手柄随动；松手后仍有 59081 px 变化，说明不是回弹。

   结论：**点击与拖拽的执行层（`canvas_actions.py`）均已 live 验证可用**。
   工具：`tools/hunt_drag.py`（持久猎取 + 探测验证）。
3. **照片网格路径未经端到端验证** —— 实测里 0 次遇到该题型。
4. **必须复用浏览器** —— 一个进程内反复 `__enter__` Camoufox 会抛
   `Sync API inside the asyncio loop`；每次试验只开新 page。
5. **选中状态只能靠像素差分读** —— DOM 里没有任何标记。
6. **选中数量有上限** —— 达到上限后点击被静默忽略，不会报错。
7. CPU 推理较慢 —— 大模型本地推理单次 106~185s（实测），不适用于实时解题。
8. 网络受限 —— 本机 GitHub / HuggingFace 直连不可用，需走代理或镜像。

### 两个环境坑（踩过，记录以免重复）

- **`page.evaluate` 跑在隔离世界**：能读 DOM，但读不到页面里定义的 JS 全局变量
  （`window.xxx` 恒为 `undefined`）。要传递数据请走 DOM 节点
  （例如把 JSON 写进某个元素的 `textContent` 再读）。
  这也意味着早先「`window.hcaptcha` 是 undefined」的观察不能作为
  「hCaptcha 没暴露 API」的证据。
- **`page.set_content()` 不执行内联脚本**：实测只写入 DOM，页面停在 `about:blank`。
  要执行脚本请用路由拦截在一个真实 URL 上提供服务。
